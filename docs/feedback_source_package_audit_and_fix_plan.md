# AgRefactor++ 错误反馈、源码包和责任判定修复计划

## 文档目的

这份文档是后续服务器修改的工作合同。每一项代码修改都必须先在当前服务器代码和真实调用链中确认问题仍然存在；如果问题已经不存在，只记录核查结果，不重复修改。

本计划不建立第二套重构系统，也不改变现有 `refactor`、`optimize`、`full` 入口。所有修复都在现有预检、候选修复、测试台修复、软件仿真、综合和协同仿真链路中完成。

核心原则：

1. 真实编译、链接、软件仿真、综合和协同仿真是复杂行为和最终阻断依据。
2. 错误正文要尽量完整地传给后续修复模型，但必须有长度上限并脱敏路径。
3. 责任归属只能来自编译器、链接器、隔离运行、结构化运行结果和工具链的明确证据。
4. 不能用固定日志关键词、固定文件名、字符串正则或样例名称猜测复杂程序责任。
5. 责任未知时保持未知，不强行归给候选或测试台，也不建立特例通行。
6. 公开测试可以在冻结前按现有次数修复；隐藏测试冻结后仍不能因为候选失败而修改。

## 一、错误反馈链

### 1. 公开协同仿真反馈

先检查以下问题是否仍存在：`flow/tools/vitis_cosim.py` 是否只返回笼统原因码，`agrefactor/runtime/cosim_stage.py` 是否没有把失败详情放进 `FeedbackItem.detail`，候选修复历史是否看不到失败用例、期望值、实际值和关键工具输出。

如果问题仍存在：

- 在现有协同仿真调用记录中保留状态、返回码、标准输出、标准错误、工具日志摘要、结构化运行结果和责任判定依据。
- 公开失败结果提供有界的诊断摘要和关键输出差异；不自行推理根因，不用正则解析成武断责任。
- 在 `agrefactor/runtime/cosim_stage.py` 中把真实诊断放入反馈详情和安全元数据。
- 保证 `agrefactor/repair/candidate_loop.py` 的每一次候选修复都携带本次详情以及之前所有失败摘要。
- 隐藏测试仍只保留应有的脱敏边界，不把隐藏输入和隐藏诊断泄露给候选修复。

### 2. 普通软件仿真异常反馈

先检查 `agrefactor/runtime/csim_stage.py` 的异常报告是否仍然只保留异常类型而没有详细内容。如果仍存在：

- 把调用记录中的编译状态、仿真状态、返回码、启动错误、标准输出和标准错误作为详细证据。
- 对外反馈只做路径脱敏和长度限制。
- 工具或环境异常仍归工具链、配置或未知，不自动触发候选修复。

### 3. 测试台覆盖率和测试台修复反馈

先检查 `flow/tools/tb_coverage.py`、`flow/tools/tb_optimizer.py` 和 `agrefactor/testing/testbench_repair.py` 是否仍丢弃标准输出，或在运行失败后不能把新错误带入下一次修复。如果仍存在：

- 同时保留 `run_stdout`、`run_stderr`、返回码、编译诊断、运行诊断和历史失败记录。
- 让测试台修复形成现有链路内的有限循环：修复、真实预检、真实运行、把新反馈带入下一次修复。
- 继续使用现有测试台修复次数和预算，不能无限重试。
- 只有真实证据明确属于测试台时才进入测试台修复；未知责任不通过猜测获得修复资格。

## 二、源码包流程

### 1. 原生软件仿真入口

先检查 `flow/tools/vitis_csim.py` 中 `make_native_vitis_csim_script()` 的签名、内部使用和调用处是否已经一致。如果参数错误仍存在，再修复 `extra_sources` 的统一传递，并把实际文件清单写入调用证据。

### 2. 所有执行阶段使用同一份源码清单

先检查额外源码是否真正进入以下阶段：

- 测试台预检编译和链接；
- 普通软件仿真；
- 综合；
- 公开协同仿真；
- 测试台修复预检。

重点核查并按实际缺口修改：

```text
agrefactor/runtime/cosim_stage.py
agrefactor/runtime/candidate_repair_integration.py
agrefactor/testing/testbench_repair.py
flow/tools/csim.py
flow/tools/csynth.py
flow/tools/vitis_csim.py
flow/tools/vitis_cosim.py
```

当前 `--extra-source` 的语义是用户明确指定的独立只读支持源码。没有明确角色时不能自动猜它属于候选还是测试台；失败应记录为源码包/配置证据，不把所有失败统一归给测试台。

### 3. 删除固定命令文本替换

先检查 `flow/tools/csim.py` 是否仍通过替换固定命令片段加入额外源码。如果仍存在，改为根据结构化源码列表生成编译命令，不能依赖固定文件名、固定命令顺序、固定输出文件名或无空格路径假设。

### 4. 缺少额外源码不能静默跳过

先检查 `flow/tools/csynth.py` 是否仍在 `os.path.isfile()` 不成立时直接跳过额外源码。如果仍存在，改为记录明确的源码包配置错误，并停止该真实执行阶段；不能把错误归给测试台，也不能让模型修改只读支持文件。

### 5. 普通单文件入口不能默认带入整个父目录

修改 `agrefactor/product/source_bootstrap.py` 前，先检查是否在没有用户明确指定源码包时把源文件父目录当作源码根目录。如果仍存在，改为只有用户传入 `--source-root` 或 `--extra-source` 时才启用源码包；普通单文件任务保持原有范围。

### 6. 模型上下文中的支持文件

先检查 `agrefactor/config/source_package.py` 是否只向模型提供头文件。如果仍存在，纳入用户明确指定的 `.cpp`、`.cc`、`.c` 等只读支持源码，保持单文件大小上限和路径范围限制。模型仍只能修改目标源码。

### 7. 源码包证据一致性

每个阶段的实际编译清单、源码相对路径和角色必须写入调用记录。证据中的清单必须与真正传给编译器或 Vitis 的文件一致，不能只复制文件而不记录或不编译。

## 三、不可靠归责和特判

### 1. 删除固定日志关键词归责

先检查 `flow/tools/tb_coverage.py` 是否仍使用以下文字决定责任或修复动作：

```text
golden reference left
golden=
reference output
original output
```

如果仍存在，删除其责任判定作用。它们只能作为普通诊断文本保留，不能决定修复测试台、重新生成桩代码或归责原程序。

### 2. 删除固定生成文件名归责

先检查覆盖率编译失败是否仍通过固定名称 `testbench.cpp`、`orig_code.cpp`、`refactor_code.cpp` 猜测责任。如果仍存在，使用本次执行生成的源码清单和角色记录对应编译器诊断；无法对应时保持未知。

### 3. 样例名称不参与主流程决策

审计主流程中不得出现根据以下样例名称放行、拒绝或改变修复次数的分支：

```text
Struct_E1_stream
Pointer_E3_double_pointer
strassen
linkedlist
c2hlsc
hlsrewritter
```

数据集盘点脚本可以记录样例名称，但不能改变普通重构主链路。

### 4. 保留的静态检查边界

只保留明确结构检查：

- 路径和源码包边界合法；
- 明确指定的文件存在；
- 结构化合同可解析；
- 模型返回完整代码块；
- 编译器、链接器和真实运行结果。

复杂接口、复杂控制流、输入合法性和错误责任不能由手写正则门禁决定。解析失败只能记录为未知或提示，不能武断阻断真实执行。

## 四、修改前后的验证要求

每项修改必须先做“问题仍存在”的代码路径核查，再做最小修改。不得根据历史描述直接改已经不存在的问题。

至少增加或执行以下回归检查：

1. 协同仿真失败详情能进入 `FeedbackItem.detail`、失败历史和候选修复提示。
2. 输出中出现 `golden=` 等文字时，责任判定不发生变化。
3. 软件仿真异常报告包含真实启动和运行证据。
4. 测试台运行失败后的新反馈能进入下一次测试台修复，且次数受现有预算限制。
5. 额外源码真正进入预检、软件仿真、综合、协同仿真和测试台修复预检。
6. 额外源码缺失被报告为源码包/配置问题，不被归为测试台。
7. 普通单文件任务不会自动复制整个父目录。
8. 没有新增样例特判、固定日志归责或复杂静态门禁。
9. 回归样例时不再按“此前通过”和“剩余”拆分 HLSRewriter；`hlsrewritter` 目录下的 20 个样例全部运行。

### 真实样例回归批次和命令形式

修复完成后的真实回归总数为 35 个：

- `heterorefactor` 下 6 个单文件样例；
- `c2hlsc` 下 9 个带支持文件的样例；
- `hlsrewritter` 下 20 个样例，全部纳入，不再遗漏其中任何一个。

每个样例单独执行一次现有 `refactor` 入口，使用唯一的输出目录和运行标识。所有批次都必须使用完整普通流程：

```bash
source /data/agrefactorpp_env.sh

python -m agrefactor.cli refactor SOURCE --top TOP \
  --public-tests auto \
  --hidden-tests auto \
  --max-testbench-repairs 3 \
  --max-candidate-repairs 3 \
  --cosim-policy required \
  --json --verbose \
  --output-dir UNIQUE_OUTPUT_DIR
```

单文件样例不传 `--source-root` 和 `--extra-source`。源码包样例必须显式传入：

```bash
python -m agrefactor.cli refactor TARGET_SOURCE --top TOP \
  --source-root SOURCE_ROOT \
  --extra-source SUPPORT_SOURCE_1 \
  --extra-source SUPPORT_SOURCE_2 \
  --public-tests auto \
  --hidden-tests auto \
  --max-testbench-repairs 3 \
  --max-candidate-repairs 3 \
  --cosim-policy required \
  --json --verbose \
  --output-dir UNIQUE_OUTPUT_DIR
```

`TOP` 必须依据该样例的真实顶层声明、配置或编译信息确认，不能按目录名猜测。`--extra-source` 只列出经过源码清单和真实编译关系确认的独立支持源文件；头文件、数据文件和配置文件保留在源码根目录中，但不被盲目当作独立编译单元。`main.cpp` 或 `tb.cpp` 不能仅凭文件名加入额外源码；若它们是测试台，则不应与自动生成测试台重复编译。

每个样例的验收除最终状态外，还必须核对实际源码清单、预检、软件仿真、综合、协同仿真、反馈历史以及隐藏测试状态。不能使用 `--hidden-tests none`，也不能只依据配置字段声称隐藏测试已执行。

### 回归执行顺序

当前工作范围先锁定为本文件已经列出的错误反馈、源码包传递、责任判定和静态门禁问题。回归期间即使发现其他与本文件无关的问题，也先记录证据，不扩大本轮修复范围。

正式运行 35 个样例前，先做三次小型真实试跑：

1. 一个 `heterorefactor` 单文件样例，验证不带源码包参数的入口；
2. 一个 `c2hlsc` 带独立支持源码的样例，验证源码包和额外源文件清单；
3. 一个 `hlsrewritter` 带依赖文件的样例，验证复杂测试台、支持文件和反馈链路。

这三次试跑仍使用上面的完整命令、自动公开测试和自动隐藏测试。它们只用于尽早发现本文件所涉及的主流程阻断，不替代完整回归。

只有三次试跑确认主流程可以继续，才运行完整的 35 个样例：6 个 `heterorefactor`、9 个 `c2hlsc` 和 20 个 `hlsrewritter`。如果试跑或全量回归暴露出本文件范围内的流程缺陷，修复后重新运行受影响的试跑和全量回归；如果是本文件范围外的其他问题，只记录，不在本轮提前处理。

最终报告必须区分：真实源代码问题、测试台问题、源码包问题、工具链问题、反馈链问题和责任未知；不能只报告“通过/失败”。

## 当前执行边界

本文件写入后，后续每次修改都必须引用对应条目并记录：

```text
核查的文件和调用路径
确认问题仍存在的证据
实际修改的文件
真实执行验证结果
```

若核查发现某项已经被其他改动解决，则不再重复修改，只记录“已解决”和证据。
