## 目标

为后续案例记录、经验整理和修复前检索定义稳定的本地数据合同，并为后续修复入口统一计数提供可测试的额度接口。P2 不接入案例采集、经验生成、经验检索、AI 诊断、目录专项检查或 Testbench 生成器；这些仍由 P3–P6 逐步实施。

本阶段通过后应能用纯本地测试表达：一个故障案例包含多次修复尝试；一次尝试失败不等于案例失败；诊断结论与责任/授权结论分开保存；证据检查有满足、缺失、矛盾三种结果；额度按案例或生成任务隔离，组合修改只计一个全局动作并分别扣组件额度。

现有 `CampaignCase` 表示评测任务中的输入案例，不是一次故障的生命周期；它不作为新 Case 复用。现有 `RepairAttemptRecord` 可继续作为某些入口的详细调用记录，但其单角色、按 run 编号的结构不足以代表跨阶段的故障案例。

对服务器 `/data/agrefactor_runs` 中截至 2026-10-12 的结构化运行记录做了只读抽样：一条 Candidate repair run 含 3 次已派发尝试，均有文件差异但验证失败；对应诊断事件跨 CSYNTH/COSIM，owner 从 Candidate 变化为 `unknown`。另有 Public Testbench repair run 只记录初始预检，`repair_attempts_used=0`，包括预检成功和 owner 不符的预检失败。该样例用于核对记录语义，不用于推断目标额度或运行总体分布；未读取 Hidden 内容、模型回复或源码正文。

## 建议的数据合同

以下是计划采用的最小字段；具体类型名可以在评审时微调，但字段间的语义边界不变。

1. `DiagnosticCase`：`case_id`、创建时间、open/closed 状态、结案结果/原因、关联 `DiagnosticEvent` 引用、按序排列的实际修复 attempts、schema version。一个 case 可跨多次修复尝试和阶段延续；新 case 使用独立额度，恢复同一个未结案 case 时保留已记额度。
2. `CaseAttempt`：`attempt_id`、case 内序号、实际派发的修复结果、修复前诊断事件引用、修复后验证/诊断事件引用、repair policy/ledger 事件引用、被请求修改的组件、适用的 Public/Hidden-generation 额度类别，以及可选的修复记录引用。预检、资格判断或在派发前被拒绝的请求不建立 `CaseAttempt`；它们可作为相关诊断/证据事件保留。实际派发后即使没有文件差异，仍建立 attempt 并按规则计数。它不复制模型响应或原始源码。
3. `EvidenceCheckResult`：登记检查标识、结果 `satisfied | missing | contradicted`、证据引用和简短的本地检查说明。它只描述诊断检查结果，不授予 owner 或 repair eligibility。
4. `OwnerAssessment` 与 `RepairEligibilitySnapshot` 分开记录：前者保存当前 owner 和可选责任线索，允许 `unknown`；后者只引用本地 policy decision、授权来源和 evidence refs。历史责任、AI 线索或目录命中均不能生成授权。
5. `ExperienceRecord`：只定义后续 P3 自动整理所需的来源字段，如 source case/attempt IDs、正向/负向类别、适用条件、实际动作、验证范围、源码版本/hash 和 evidence refs。不在 P2 生成经验。经验没有自动生命周期或人工晋升状态；人工审核状态属于“经验能否晋升为正式目录规则”，不属于经验本身。

序列化数据只保存必要的结构化摘要、稳定引用和 hash，不写入整段源文件、隐藏评测内容、原始模型响应或任意服务器路径。`unknown` 可以作为诊断/owner 当前状态保留；结案后是否形成经验取决于案例结局和具体尝试的验证证据，不能因为 owner 曾为 `unknown` 就改写成已知根因。整个 case 未解决时不产生可检索 ExperienceRecord。

## 建议的组件额度接口

正式修复仍由 `RecoveryPolicy` 决定资格；Testbench 生成资格修正仍先通过生成流程现有的 Public/Hidden qualification contract。额度接口只在对应本地授权/资格门通过后原子记账，不能推断 owner、改变资格、放宽 Hidden 边界或挑选修复路线。P2 不合并这两种授权合同。

建议在现有 `RecoveryLedger` 中增加描述目标额度的 `RepairComponentLimits`、单次动作的 `RepairActionCharge` 和两阶段修复动作 API。新额度只被新增 API 使用，现有 `reserve()` 和其调用方不读这些配置：

```python
authorization = current_local_gate(request)  # RecoveryPolicy or generation qualification
charge = RepairActionCharge(
    scope_id=case_id,
    logical_action_id=action_id,
    components=("candidate",),
    visibility="public",
    authorization_ref=authorization.event_id,
)
reservation = ledger.reserve_component_action(charge)
if final_local_gate_rejects:
    ledger.release_component_action(reservation)
else:
    # Commit at the exact point the authorized repair request is dispatched.
    ledger.commit_dispatched_action(reservation)
    dispatch_repair_request(reservation)
```

`RepairActionCharge` 携带不含内容的 `authorization_ref`，指向已通过的 policy decision 或阶段资格记录。预留/提交接口只做预算核验和记账；实际调用方负责先通过对应本地授权门。正式 Hidden evaluation 没有可接受的授权引用，仍必须在现有 policy 门被拒绝；Hidden-generation 只允许沿其现有生成资格路径记账。

字段和操作语义：

- `scope_id`：常规故障使用稳定 `case_id`；Testbench 生成任务使用任务级 ID，让同一任务中的 trajectories 共享相应额度。不同 case/任务互不消耗额度。
- `logical_action_id`：同一个逻辑修复动作只创建一个 reservation。若同时改 Testbench 与 Stub，全局动作计一次，两个组件各计一次。
- 组件额度桶：Candidate；Testbench Public、Testbench Hidden-generation；Stub Public、Stub Hidden-generation。Hidden-generation 只作为计数类别，不允许保存或跨 case 传播生成内容/反馈。
- reservation 先原子检查并占住全局动作位和全部目标组件额度，防并发超额；所有本地门通过后，在修复请求实际交给 repairer/provider 的派发边界提交计数。调用方确认不会派发或在派发前被本地拒绝则释放、不扣额；派发后即计数，即使调用失败或最终没有文件差异。
- 正式 Hidden evaluation 仍由现有 `RecoveryPolicy` 拒绝。Hidden-generation 额度不能作为授权信号，也不能被用于正式 Hidden 评测后的修复。
- Case/任务恢复时从已提交 action 记录恢复额度；新 scope 从零开始。提交、释放和重复提交均需有明确的幂等行为。
- `RepairComponentLimits` 的合同测试采用 v0.3 已确认的目标数值：Candidate 3；Testbench Public/Hidden 各 3；Stub Public/Hidden 各 3；Lightweight 全局动作上限 15。P2 不改当前产品默认额度；现有 `RecoveryLimits.total_recovery_actions=5` 和未接线的 `tb_optimizer` 局部计数留待 P6 接入时统一调整。

为避免改变现有生产行为，本阶段保留 `RecoveryLedger.reserve()` 的既有即时记账语义；新增组件额度 API 接收已经过本地授权门的 `RepairActionCharge`，暂不改变现有调用者。P6 迁移实际 Candidate、Testbench 正式修复和 `tb_optimizer` 生成资格修正入口时，再逐个切换到统一组件额度合同并验证行为。

## 验收测试

新增单元测试至少覆盖：

- case round-trip、重复 attempt ID/序号拒绝、未知 owner 与可选线索并存、尝试失败与 case 未解决/已解决分别表达。
- 证据结果仅接受 `satisfied`、`missing`、`contradicted`；三种结果均保留 evidence refs，不能改变 owner 或授权。
- 已解决 case 可引用有验证依据的正向来源；明确动作级失败且同一 case 后来解决时，才可引用窄范围负向来源；未解决 case 不产生可检索经验。已解决但 owner 仍为 `unknown` 的 case 可以保留 unknown 并记录可验证的动作结果，不得擅自补写根因；来源 case/attempt/hash 可复现。
- 单组件派发扣对应组件额度与一次全局额度；Testbench+Stub 一次逻辑动作全局计一次、组件各扣一次；Public/Hidden-generation 分账；不同 case 独立；同一 case 恢复后沿用已提交用量。
- 预检成功/失败但没有派发修复请求时，不建立 CaseAttempt 且不扣修复额度；授权拒绝不扣额；预留后派发前拒绝会释放；实际派发后即使 `changed=False` 仍建立 CaseAttempt 并计数；重复提交不会重复计数；并发预留不能超过任一组件桶或全局桶。
- 正式 Hidden evaluation 继续被 RecoveryPolicy 拒绝；Hidden-generation 只能计入独立额度，不能写入 agent-safe case/experience payload。
- 既有 Candidate、Testbench、Hidden recovery policy 和 `RecoveryLedger.reserve()` 行为不回归。

## 风险、回滚与评审项

- **Case ID 与 quota scope 的来源。** 本计划规定常规修复由稳定 case ID 隔离额度、生成任务由 task ID 共享额度；P3/P6 再负责由实际入口提供这些 ID。P2 不修改 run ID / lineage ID 的生成路径。
- **现有 reserve 语义。** 新 API 为后续入口提供两阶段记账，但旧调用继续即时计数。P6 迁移时需防止同一动作同时走两套 API。
- **持久恢复。** P2 定义稳定 action 记录和从已提交记录重建计数的接口；case 文件的真实持久化/追加写入由 P3 实施。单纯重建 ledger 不允许将原始 Hidden 内容带入 Case。
- **API 范围。** 若同一 ledger 可能由多进程并发使用，仅实例内线程锁不足；P2 先按当前线程池共享同一 ledger 的运行方式设计。跨进程共享账本需要独立持久化/锁方案，不在本阶段假设已解决。
- **回滚。** P2 只增加新数据类型与未接线的额度 API，并保留旧入口语义。出现回归时可撤回新增类型/API 和对应测试，不需恢复服务器运行产物或改动用户已有文件。

**执行结果（2026-10-15）：** 本计划已获认可并完成实现。指定的 7 个测试模块复跑共 87 项通过，`git diff --check` 通过。P2 只交付数据合同和额度接口，没有把接口接入生产修复入口；该边界符合本计划范围。
