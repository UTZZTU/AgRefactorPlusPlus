# 历史失败盘点与修复范围计划

> 版本：v0.1（待审阅）
> 日期：2026-10-17
> 状态：H0--H5 已按用户确认范围实施；剩余失败已隔离为 legacy 范围
> 适用分支：`backup/server-current-20261013`

## 1. 目的与边界

本计划处理 v1.1 全量测试中已经在实施前基线存在的失败和错误，回答三个问题：

1. 哪些条目是测试夹具或测试合同过时，应该更新测试；
2. 哪些条目反映当前主流程合同仍需核定或修复；
3. 哪些条目属于旧 R4/R5 实验、生成物或历史数据合同，应该隔离、单独维护或另行退役。

本计划不是 P6 统一额度账本实施计划，也不提前实现新的修复。它不把历史失败自动转成新记忆系统的经验，不把目录规则改成 owner 或修复授权门，不以降低 Public/Hidden 安全边界来消除测试红灯。

服务器操作约束保持不变：同一个 shell 中先执行 `source /data/agrefactorpp_env.sh`，再进入 `/data/AgRefactor`。当前服务器存在 `.orig`、`.rej`、备份目录和运行产物；这些不属于本计划的清理范围。

## 3. 分级原则

### 3.1 先核对合同，再决定改哪里

- 测试构造对象缺少当前生产代码已经要求的字段：优先补齐 fixture/factory 和断言；不使用生产代码中的静默 `getattr` 放宽合同。
- 测试期望与 v0.3 已确认的安全行为冲突：先确认事件证据和状态转换，再更新断言或把测试移入 legacy suite；不为了满足旧断言而放宽 owner、evidence、Hidden 或 budget gate。
- 生成的 JSON 与 builder 不一致：先做结构化 diff 和确定性检查，再决定更新 checked-in artifact 还是修 builder。
- 只有当完整、可信的测试输入证明主流程丢失已承诺行为时，才进入生产代码修复包。

### 3.2 统一的安全边界

- `unknown`、`review_required` 和 `rejected` 不能仅凭旧测试期望互换。
- 诊断目录只提供类别和诊断重点；不能因为目录命中而直接授予 owner、修复权限或预算。
- 正式 Hidden 评测后的修复保持禁止；Hidden 生成期和正式 Hidden 反馈继续按现有投影边界区分。
- 旧 R3/R4/R5 episode、lifecycle、snapshot-bound memory payload 不是新 Case/Attempt/Experience 合同；旧实验应隔离，不直接接入新 P6/P7。
- 本轮不把真实 HLS 运行当作修复这些单元测试合同问题的前置条件。真实案例只在代码/测试合同稳定后用于 P7 验证。

## 4. 历史失败分组与修复范围

### A. 测试夹具或数据合同漂移：优先更新测试

**大致规模：16 个 errors，主要集中在 4 个模块。** 这些条目当前生产代码已经使用更完整的类型合同，错误来自旧 fixture 未同步。

涉及模块和事实：

| 模块 | 代表条目 | 真实原因 | 计划动作 |
|---|---|---|---|
| `test_depth_contract_additions.py` | `test_zero_request_prune_does_not_discard_unused_public_repair_quota` | `SimpleNamespace` 缺少真实 `TestbenchRepairResult.attempts` 字段 | 补齐 fixture；保留额度合同断言 |
| `test_legacy_effective_config_translation.py` | 5 个 CLI builder 测试 | fixture 缺少 `record_diagnostic_cases`、`diagnostic_assist` 等新增配置属性 | 在测试 factory 中提供默认值；验证独立开关仍默认关闭 |
| `test_model_family_profile.py` | `test_candidate_loop_derives_profile_from_fixed_adapter` | selected feedback 不是完整 Candidate-owned/authority evidence | 构造完整合格反馈；不降低 profile 推导前门 |
| `test_p4_0b_r_optimize_recovery.py` | 9 个 coordinator/eligibility 测试 | `OptimizeRecoveryEvidence` 缺少 `route_decision.action=REPAIR_CANDIDATE`、agent-safe、blocking feedback 等强制字段 | 统一使用合法 evidence factory；分别覆盖 budget blocked、route mismatch、success 和 semantic unchanged |

验收要求：A 组每个测试用例都能说明缺哪个合同字段；生产函数签名、严格校验和 `unknown/review_required` 行为不因测试方便而放宽。

### B. 当前主流程的证据、路由和可见性合同：先核定，再决定测试或生产修复

**大致规模：约 14--16 个 failures。** 这组不是简单的“旧断言全改成新断言”，需要把完整事件输入、当前状态机和 v0.3 语义对齐。

涉及模块和问题：

- `test_feedback_coordination.py`
  - `test_preflight_testbench_repair`
  - `test_csynth_candidate_repair`
  - `test_hidden_candidate_failure_is_suppressed`
  - Public Candidate/Testbench fixture 缺少完整 owner authority/evidence/tool execution 元数据，当前返回 `review_unknown` 或 `review_required`。
  - Hidden 结果当前偏向 operator-only 和 `review_required`；必须先确认 v0.3 对该事件的终态语义，再决定断言是否应改为 `review_required`，不能仅为通过测试改成自动 `REJECTED` 或自动修复。
- `test_optimizer_qualification.py`
  - 7 个 preflight/public/csynth/baseline 条目将不完整的 `fail_report()` 当成确定拒绝。
  - 生产资格代码要求 `physical_execution` 之外的 agent-safe、authority、route/report、blocking feedback 等证据；应分别补齐“证据完整且明确失败”和“证据缺失需复核”的 fixture。
- `test_test_evaluation_feedback_composer.py`
  - Public Candidate failure fixture 缺少确定性 Candidate authority；Hidden composition 期待 `rejected`，但当前 operator-only 边界可能应为 `review_required`。
- `test_validation_orchestrator.py::test_hidden_data_not_in_result_or_trace`
  - 继续保留不泄露 Hidden 数据的断言；先确认 Hidden 的终态是拒绝还是人工复核，不能用结果状态改变隔离合同。
- `test_modern_effective_config_migration.py::test_repair_prompt_uses_resolved_instruction`
  - 检查 `accepted=False` 是否来自旧 fixture 不满足当前 Prompt/validation 合同；若是，修 fixture；若是真实回归，才进入生产修复。

实施前的核定矩阵必须至少记录：输入 visibility、owner、authority evidence、execution evidence、route、预期 policy decision、预期 validation state。只有矩阵证明生产行为偏离 v0.3 才允许改生产代码。

### C. 旧 R4/R5 实验路线：隔离处理，不混入新系统

**大致规模：约 40 个 unittest 条目，包含重复 discovery；不是 40 个独立生产缺陷。**

涉及范围：

- `test_r4_existing_orchestrator_integration.py` 及 `tests.test_r4_existing_orchestrator_integration`
  - 依赖旧 `episode_path`、`verified_positive/verified_negative/inconclusive`、calibration certificate、snapshot revision、provenance 和 authorization 合同。
  - 同一测试文件被两条导入路径发现，需先修 discovery/模块命名，避免重复计数。
- `test_r5_existing_orchestrator_integration.py`
  - A2--A6 authorization、snapshot、lifecycle、memory payload 断言与当前 strict gate/abstain 行为不一致。
- `test_r5_product_campaign_executor.py::test_all_arms_consume_one_capture_with_isolated_usage`
  - 旧 campaign 的 capture/usage 隔离合同需要单独判断是否仍为维护目标。

处置范围：

1. 先建立 `legacy` 测试标识和唯一 discovery 清单，不让重复发现继续扩大统计；
2. 每个旧套件单独决定“按旧合同修复”“冻结为历史回放”“标记不再维护”三者之一；
3. 若继续维护，只在旧模块边界内修复其 episode/snapshot/lifecycle fixture，不把旧 schema 转成新 Case/Experience；
4. 不在 P6/P7 前顺手删除旧代码、运行数据、`.orig/.rej` 或备份；清理另建引用/配置/数据盘点计划。

完成条件不是把 R4/R5 全部改绿，而是每个套件有明确维护状态、唯一发现计数和与新系统隔离的验收命令。

### D. 生成协议与数据注册表：先核对生成物，再决定 builder 或测试

涉及两项：

- `test_inheritance_stage3.py::test_committed_protocol_matches_builder`
  - 对 `configs/inheritance/stage3/protocol.json` 和当前 builder 输出做结构化 diff。
  - 若 checked-in artifact 过期，重新生成并记录生成器版本/输入 hash；若 builder 非确定或输出错误，修 builder 并补确定性测试。
- `test_r5_1_dataset_registry.py::test_execution_sources_participate_in_global_dedup`
  - 当前 `dataset_registry.json` 含 inconsistent execution contract 字段，但 `d0_case_count`、`d1_case_count` 均为 0，旧测试期待至少两条。
  - 对照 `r5_1_build_dataset_registry.py`、`deduplication_policy.json`、`src/info.json` 和输入 execution sources，判断是数据政策已改变还是 builder 漏掉 execution-source dedup；不能只把数字断言改成 0。

验收要求：生成器重复运行结果稳定；提交的生成物与 builder 输出可由同一命令复现；数据政策和 fixture 来源写入测试说明。

### E. 旧 P0/P4 文本或行为硬编码断言：改为行为断言

涉及四项：

- `test_p0_step_d_prompt_error_ownership.py::test_stub_prompt_declares_unique_candidate_implementation`
  - 当前 prompt 使用语义等价的 “Attempt to correct only the Stub”，测试不应依赖旧字面 “Repair only the Stub”。改为检查唯一 Stub 作用域和禁止 Candidate 修改的语义。
- `test_p0_step_e_repair_budget_parameterization.py::test_no_no_progress_early_stop_is_added`
  - 当前实现按 `while repair_count < request.max_attempts` 继续到额度耗尽，符合 v0.3；测试应验证失败后仍可继续到额度耗尽，不检查源码字符串 `request.max_attempts + 1`。
- `test_p4_0f_r5_ab_csynth_hls214.py::test_recognized_item_routes_to_candidate_repair`
  - 当前设计明确目录分类不单独授予 owner/修复权限；测试应验证目录提供诊断焦点但完整 owner evidence 仍是必要条件，或将旧 R5 期望移入 legacy suite。
- `test_provided_qualification_result_contract.py::test_generated_mode_remains_legacy_default`
  - `TestbenchGenerationExhausted` 只有所有 trajectory 真正耗尽才为 true；普通 compile failure 不能被强行标成 retry exhausted。补齐生成模式 fixture 并分别断言 provided/generated 语义。

## 5. 推荐实施顺序

### H0：冻结盘点资料

### H1：修复 A、E 测试合同

- 先改 fixture/factory 和行为断言，保持生产安全门槛不变。
- 运行 A/E 定向测试，再运行 P2--P5 已冻结的定向集合。

### H2：核定 B 的 Public/Hidden/unknown 语义

- 为每项构造完整 authority/evidence matrix。
- 若完整输入下生产状态仍违背 v0.3，再提出最小生产修复计划；否则只更新测试。
- 单独验收 Hidden 不泄漏、unknown 不自动授予权限、review_required 不被误判为成功。

### H3：隔离并处理 C

- 先消除重复 discovery，再为 R4、R5、R5 campaign 建立独立命令和维护状态。
- 旧套件的修复或退役须另行批准，不阻塞新 Case/Experience、P6 账本和 P7 试运行。

### H4：核对 D 生成物

- 结构化 diff、重复生成、输入 hash 和政策审查完成后，决定更新 artifact、修 builder 或更新旧 fixture。

### H5：重跑并更新路线状态

- 分组定向测试通过后再跑全量 unittest。
- 把剩余失败按“仍属历史遗留 / 当前生产缺口 / 已明确退役套件”重新记录。
- 更新 v0.3 的执行状态和单独的差异记录；不把尚未实施的 P6/P7 标为完成。

## 8. 已确认的实施决策

用户已接受以下五项决策，本计划已据此在服务器实施：

1. **A/E 第一批按测试合同修正。** 更新 fixture/factory 和行为断言，保持生产代码的严格证据、权限、Hidden 和额度合同；不使用生产代码静默兼容来消除失败。
2. **B 先建立证据矩阵再改预期。** `review_required` 用于证据不完整或需要人工复核的情况；只有证据完整且明确触发禁止策略时才使用 `rejected`。Hidden 不泄漏断言必须保留。
3. **R4/R5 暂时隔离为 legacy suite。** 先消除重复 discovery、建立唯一计数和维护状态；不把旧 schema 接入新 Case/Experience，不立即删除旧代码或数据。继续维护、冻结回放或退役在独立盘点后决定。
4. **D 先做结构化 diff 和重复生成。** builder 正确而提交生成物过期时更新 artifact；builder 不稳定或错误时修 builder；输入政策已变更时更新 fixture/测试说明。不得只修改数字断言掩盖生成缺陷。
5. **接受 H0--H5 顺序。** 先冻结基线，再处理 A/E、核定 B、隔离 C、复核 D，最后分组验收并重跑全量测试。

这些决策授权本计划的范围内修复。每个 H 阶段仍须在执行记录中列出实际文件、命令、测试结果和未解决项；超出上述边界的生产行为变化、旧模块退役或真实 HLS 实验需要另行计划。
