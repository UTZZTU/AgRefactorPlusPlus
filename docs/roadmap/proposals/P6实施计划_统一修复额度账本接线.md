## 3. 额度合同

### 3.1 Lightweight 基线

Public 与 Hidden-generation 各一条有效 trajectory。额度按组件和可见性分桶：

| 桶 | 基准额度 | 覆盖动作 |
|---|---:|---|
| Candidate | 3 | 同一 Case 中跨 Preflight、CSIM、CSYNTH、COSIM 和不同修复路线的 Candidate 修复。 |
| Testbench Public | 3 | 正式 Public Testbench 修复与 Public 生成资格修正共用。 |
| Testbench Hidden-generation | 3 | 仅允许的 Hidden 生成期资格修正；正式 Hidden 评测反馈修复仍禁止。 |
| Stub Public | 3 | Public 生成中实际修改 Stub 的修复或重生成。 |
| Stub Hidden-generation | 3 | Hidden 生成中实际修改 Stub 的修复或重生成。 |

不发生 Testbench+Stub 组合动作时，全局逻辑修复动作上限为 15。一个逻辑动作同时改 Testbench 和 Stub，全局计一次、分别扣两个组件桶。

### 3.2 `M` 扩展

同一个生成任务中的 trajectories 共用任务级额度池，不为每条 trajectory 复制额度。`M_public`、`M_hidden` 必须取 profile 解析后的有效值：

- Candidate 始终为 3，不随 generation trajectory 数变化。
- Testbench/Stub 生成额度分别按可见性线性扩展：Public 为 `3 × M_public`，Hidden-generation 为 `3 × M_hidden`。正式 Public Testbench 修复进入同一个 Public Testbench 桶。
- 五桶均启用时，该额度 scope 的全局动作上限为 `3 + 6 × M_public + 6 × M_hidden`；两边 M 都为 1 时等于 15。未启用的生成路径不产生可扣动作；正式 Public Testbench 路径至少保留 3 次基准额度。若某 scope 未启用全部组件，实际可用动作自然受启用的组件桶总和限制。
- 扩大 M 只扩大对应生成任务的 Testbench/Stub 桶和全局上限，不扩大 Candidate，也不影响独立 Case/task。

复用 `source_bootstrap`/`flow.new` 已解析的有效生成设置，不新增 CLI 开关，不改变 trajectory 默认值。15 是每个逻辑 Case/task scope 的上限，不是服务器所有案例共用的全局池；N 个独立 Case/task 各自记账。

### 3.3 计次语义

- 资格门通过且语义修复请求实际交给 repairer/provider 时提交额度。派发后 provider 报错、无效结果、无文件差异或验证失败仍扣一次。
- 授权拒绝、额度不足、诊断/预检、初始生成、普通 refinement、纯格式重试及未进入 repair 请求的验证操作不扣额。
- 一个 Testbench+Stub 联合动作使用一个全局逻辑动作 ID，charge 同时包含两个组件桶；重放同一动作必须幂等。
- 在本地门通过后，原子预留全局名额及全部目标组件桶；未派发则释放，派发则提交。并发时任一桶额度不足，整体拒绝，不部分扣额。
- 额度 enforcement 始终运行，不依赖 `--record-diagnostic-cases` 或 `--diagnostic-assist`。Case 记录开启时 Attempt 引用额度事件；关闭时仍保留防止 scope 超额所需的本地计数状态。

## 4. 接线方案

### 4.1 RecoveryLedger 与派发顺序

复用 `agrefactor/recovery/policy.py` 的 `RepairComponentLimits`、`RepairActionCharge`、`reserve_component_action()`、`commit_dispatched_action()`、`release_component_action()`、`restore_committed_component_actions()` 和 `component_action_snapshot()`。这些 API 负责额度，不负责批准修复；charge 必须引用真实本地授权决定。

在当前 RecoveryLedger 上增加最小 repair-action 接入：保留 `RecoveryPolicy.decide()`、现有 restart/token budget 门和 RecoveryDecision 留痕，然后走 P2 组件额度 API。对于 `REPAIR`，旧 `refactor_candidate_repairs_total`、Candidate CSIM/COSIM stage lane、Testbench Preflight/CSIM/COSIM lane 和 `run:total_recovery_actions` 计数都迁出，不再成为组件桶以外的第二额度来源；否则旧 lineage 计数会让独立新 Case 继承旧次数，或旧 5 次上限提前拦截。旧 `reserve()` 继续服务 P6 范围外的恢复动作，非修复动作的既有 stage/lineage 计数保持不变。

Candidate 当前旧 `reserve()` 在模型响应之后。P6 将必要的策略/budget 检查和组件额度 reserve 移到本轮 provider dispatch 之前，使额度耗尽时不会先调用模型再拒绝结果。这相对 P3“暂不移动旧 reserve”是本阶段明确的顺序变更；P3 的追溯合同继续有效：`FeedbackRouteDecision` 与 `RecoveryDecision` 是两个不同事件、分别关联。dispatch 后的模型和验证结果仍写入 CaseAttempt。

旧 `total_recovery_actions=5` 不得成为组件修复的隐形上限。不能仅将它改为 15 后继续双计。非组件 toolchain retry、validation restart 不属于五个组件桶，保持现有策略行为。

### 4.2 修复入口

| 文件 | 预期改动 |
|---|---|
| `agrefactor/repair/candidate_loop.py` | 每轮 Candidate 修复在真实 dispatch 前检查现有授权/budget 并 reserve Candidate 桶；dispatch 后 commit，dispatch 前异常 release；保留 route 与 RecoveryDecision 分开追溯。 |
| `agrefactor/runtime/candidate_repair_integration.py` | 创建并传递 Case scope ledger；Candidate 和正式 Public Testbench 共用；收敛为配合旧总上限而做的动态放大逻辑。阶段资格、owner 和路由不变。 |
| `agrefactor/testing/testbench_repair.py`、`agrefactor/testing/model_testbench_repairer.py` | 正式 Public 资格门通过后按可信 Public split reserve Testbench Public 桶，在实际 provider dispatch 处 commit；禁止新增正式 Hidden 修复入口。 |
| `flow/new.py`、`flow/tools/tb_optimizer.py`，必要时 `agrefactor/product/source_bootstrap.py` | 为同一生成任务所有 trajectory 传入共享 ledger；M 取有效配置。Testbench/Stub repair 按实际修改组件和可信 split charge。 |
| `agrefactor/runtime/repair_phase.py` 与现有 Case/生成工件写入点 | 保存 scope 限额、reserve/commit/release/reject 事件和最终摘要。CaseRecorder 可选，quota enforcement 不可选。 |

`tb_optimizer` 的语义 repair 才计额度：Testbench 单修扣对应 Testbench 桶，`regenerate_stub` 扣 Stub 桶，联合修复一个全局动作并扣两个组件桶。初始生成、refinement、格式重试仍只是 P3/P4 定义的 request event。既有 `max_repairs` 可以作为更紧的局部上限，但不能代替共享账本或绕开它。

Hidden-generation 只在生成器自己的本地范围使用 Hidden-generation 桶。额度事件不携带 prompt、源码差异、诊断、验证反馈或 trajectory 内容，不进入 Public Case/Experience。额度不授予正式 Hidden 评测反馈修复权限。Stub 保持附属生成流程，不把 `STUB` 加入 `FeedbackOwner`。

### 4.3 Scope、持久化和恢复

- 普通故障按稳定 Case/quota scope 计账；同一未结案 Case 跨阶段、跨入口延续额度，独立新 Case 从零开始。CaseRecorder 关闭时仍须有稳定运行级 scope ID。
- 同一生成任务的 Public/Hidden trajectories 共用 task scope 和 ledger，靠组件桶隔离可见性；trajectory ID 仅区分尝试。若生成资格修正是同一未结案 Case 的延续，task scope 必须绑定该 Case 的 quota scope，使正式 Public Testbench 修复与生成资格修正共用 Public 桶；若它是独立生成任务，则使用稳定 task scope。不同 Case/task 不共享。
- 使用稳定 `scope_id`、`logical_action_id` 从本地已提交 action 记录恢复。优先复用 CaseStore/生成任务工件的追加或原子写入；若 Case 记录关闭时无法保存额度状态，增加仅包含 action ID、组件桶、授权引用、状态的 sidecar，不写内容数据。
- 持久化和恢复幂等，并保护并发 trajectory。实施前需确认当前入口是否支持跨进程并发；若支持，同一 scope 必须有跨进程原子写保护，线程锁不足以证明此合同。
- `effective_repair_quota.json` 保持最终审计摘要，不作为唯一的派发前账本，也不能只在修复结束后才保存。

## 6. 冻结验收

新增或补齐以下行为测试：

1. Candidate 多阶段共享同一 Case 的 3 次额度；第 4 次必须在 provider dispatch 前拒绝。
2. 正式 Public Testbench 与 Public generation 修正跨入口共用 Public 桶；正式 Hidden 评测反馈后的修复仍被 `RecoveryPolicy` 拒绝。
3. Hidden-generation Testbench/Stub 只扣各自 Hidden 桶，Public/Hidden 不互挪；Hidden quota 工件不含内容数据且不进入跨案例经验。

## 7. 风险与回滚

- **Candidate 顺序改变：** pre-dispatch 额度检查改变旧 reserve 时序。回归 prior-attempt prompt、CaseAttempt 序号、provider failure，且 route 与 RecoveryDecision 仍分开记录。
- **旧全局上限双重生效：** 组件账本达到 15 时旧限制不能提前挡住合法修复，旧/新接口也不能重复计数。
- **scope 错误：** 不能用 trajectory ID 分裂并发池，不能仅用 root-run ID 合并独立 Case。CaseRecorder 关闭不能让 enforcement 失效。
- **Hidden 越界：** Hidden-generation 只存最小额度元数据；正式 Hidden 反馈仍不进入修复、Case、Experience 或 AI prompt。
- **回滚：** 分入口接线并验收；回滚只撤 P6 代码、测试及新增 quota sidecar，不删既有 Case、运行记录、R3/R4/R5 数据或服务器备份。
- H0–H5 后的 15 failures、3 errors 不纳入 P6 修复，只比较 P6 是否改变其状态。

## 8. 已确认决策

1. Candidate 额度在 provider dispatch 前预留；route decision 与 RecoveryDecision 继续分别留痕。
2. Candidate、Testbench 和 Stub 修复由 Case/task scope 下的组件账本计数；旧 `total_recovery_actions=5` 不再限制组件修复，非修复 retry/restart 保留原策略。
3. Case 记录关闭时仍在阶段配置的工作根目录保存最小 quota 状态，不记录诊断、源码或模型内容。
4. 有效 M 只扩展对应 Public/Hidden generation 的 Testbench/Stub 桶和 scope 全局上限，Candidate 保持 3；独立 Case/task 不共享额度。
