## 结论摘要

当前项目已经有阶段解析器、诊断分类目录、基于执行和源码来源的 owner 证据、修复资格与策略门、Candidate 修复循环，以及旧版 R3/R4/R5 记忆实验组件。它们能支持新系统的许多底层工作，但尚未构成 v0.3 描述的完整流程。

最主要的实现差距有四个：

1. 目录匹配目前主要提供分类和元数据；目录的 `evidence_requirements`、`allowed_actions` 没有形成“专项证据检查计划→检查结果→修复路由”的闭环。COSIM 目录项目前没有发现生产匹配调用。
2. 当前有 CSYNTH bounded trial 和 CSIM/COSIM public reference qualification 等受控资格路径；它们不由目录命中决定。CSIM、COSIM 的普通 Candidate 修复仍由阶段证据、owner/authority 和既有修复策略共同决定。
3. Candidate 修复额度已有跨阶段聚合；Testbench 正式 Public 修复仍按 Preflight、CSIM、COSIM 分开计数，`tb_optimizer` 的生成资格修正则按 trajectory 本地计数。当前没有 v0.3 要求的 Public/Hidden 两本 Testbench 组件账本。
4. 旧 R3/R5 episode、pattern lifecycle 和 Candidate prompt memory 接口确实存在，但普通产品默认关闭。没有统一 Case/Attempt 记录、新设计的结案经验整理开关，或在每次修复尝试前基于最新状态重新检索并注入经验的产品流程。

详细状态见下方审计清单。代码可以确认当前行为，但不能单独决定检索算法、证据阈值、额度数值、旧 R5 生命周期是否彻底弃用，以及 CSIM fallback 分支是否需要改动。

## 1. 分类目录与路由

`diagnostic_catalog.py` 将规则定义为阶段和类别分类，不分配 owner。规则 `owner_policy` 必须是 `resolve_from_evidence`；Hidden 规则不会向 agent 暴露修复动作（`agrefactor/evaluation/diagnostic_catalog.py:167-201,269-294`）。目录允许配置证据字段和动作字段，但它们目前是有限值的元数据，不是可执行检查清单。

生产调用位置如下：

- CSYNTH 日志由 `CsynthDiagnosticParser` 匹配 catalog，并把 `diagnostic_id`、`evidence_requirements`、`allowed_actions` 放入诊断记录（`agrefactor/evaluation/csynth_diagnostics.py:135-164`）。
- Staged preflight compile/link 和 Testbench preflight compile/link 会匹配相应阶段规则（`agrefactor/evaluation/staged_preflight.py:459`，`agrefactor/evaluation/testbench_preflight.py:309-312`）。CSIM 原生编译失败分类也会复用 compile/link 分类器。
- `configs/diagnostic_catalog.json` 有 `cosim_runtime_contract_interface_mismatch` 规则（约第 59 行），但 COSIM 生产路径在 `cosim_stage.py` 手工生成合同证据和 failure kind；没有发现它调用 `load_catalog()` 或 catalog matcher。

`FeedbackRouter` 的主要修复选择依据是规范化的 category、owner 和少数资格元数据；代码没有读取 `diagnostic_id`、`evidence_requirements` 或 `allowed_actions`（`agrefactor/evaluation/feedback_routing.py:205,456-493`）。因此目录目前不是完全无用：它会统一诊断类别、摘要和身份，并可帮助呈现/审计；但命中规则还不会自动选择专用证据检查或验证合同，也不会决定修复路线。

目前尚未发现通用的“三态证据检查结果”（满足/缺失/矛盾）及规则检查 dispatcher。目录里的证据字段与运行时实际证据之间没有统一核验器。所以 v0.3 的“命中后少走弯路”闭环是明确的待实现项，不应描述成当前已有能力。

## 2. 三个阶段的真实流程

| 阶段 | 诊断与 owner 证据 | 可进入的修复路径 | 关键边界 |
|---|---|---|---|
| CSYNTH | Vitis 日志/报告经 `csynth_diagnostics.py`、`csynth_artifact_feedback.py` 结构化；source location、compile unit、执行证据用于 owner 判断。 | owner 被本地证据确认时走通用 Candidate repair loop；owner unknown 时只有满足 bounded trial 合同才可能进入 Candidate repair。 | catalog 分类先于资格判断，但目录匹配本身不决定资格。没有 CSYNTH Testbench 修复循环。 |
| CSIM | native compile failure 可从 invocation/build manifest 校验 source role、compile unit、hash；功能失败看执行与 evaluated cases；Public unknown-owner runtime failure 可尝试 Original 隔离资格验证。 | Candidate、Testbench 或 unknown-owner + `public_reference_qualified` 分别由 route/policy 门决定；Candidate 修复走现有共享编排。 | CSIM runtime 错误不会普遍按目录文本匹配；compile/link 分类可能复用 catalog。 |
| COSIM | runtime contract/interface evidence、工具启动/完成状态、结果分类和 Public reference qualification；owner 从阶段结构化结果取得。 | Candidate、Testbench 或经过 Original 隔离资格验证的 unknown-owner Candidate 路径；均仍受验证和额度门控制。 | 有 COSIM catalog 配置项，但运行时没有发现 catalog matcher；不应误写成 COSIM 已按诊断目录分类。 |

### CSYNTH bounded trial 的实际顺序

`csynth_stage.py` 在解析出 blocking feedback 后，只有 CSYNTH 失败、物理执行完成且非零退出、非 timeout、所有 blocking item owner 都是 unknown 等条件成立时，才调用 `_public_reference_qualification`。通过后标记 `public_csynth_bounded_trial`、`repair_eligible=true`，再由 FeedbackRouter 形成 Candidate route（`agrefactor/runtime/csynth_stage.py:244-284`）。

这条路径与确定性 owner 已证明后的通用 Candidate repair 是两种授权条件，不是两个修复引擎。bounded trial 是 CSYNTH 特有的 unknown-owner 有界例外；它不是目录命中后的步骤。命中与未命中目录都不会改变上述先后关系。

### CSIM/COSIM 的 reference qualification

- CSIM 只对 Public runtime failure 的部分 unknown-owner 情形执行隔离验证；编译失败、工具启动/配置失败等条件不会走该分支。验证结果通过后记录 `public_reference_qualified` 并设置 repair eligibility（`agrefactor/runtime/csim_stage.py:720-747`）。
- COSIM 的资格分支要求 unknown owner、工具及 COSIM 均已启动、非 timeout、存在证据摘要，并排除运行合同接口 mismatch 等分支；之后用 Original 隔离运行，成功才标记 `public_reference_qualified`（`agrefactor/runtime/cosim_stage.py:477-505`）。
- 这两种 authority 是 Candidate 修复的阶段特有资格信号，不会把 `FeedbackOwner.UNKNOWN` 改写成 Candidate。router 再结合 repair eligibility、工具启动和 evidence complete 决定是否路由。

### CSIM 编译 owner 映射分支

`infer_failure_owner()` 在没有 `source_roles` 或 `work_dir` 时直接返回 UNKNOWN（`agrefactor/evaluation/testbench_preflight.py:353-368`）。`csim_stage.py` 的 `tb_compile_failed` fallback 调用时只传 `diagnostics`（约第 1062-1084 行），因此它无法区分报错文件属于 Candidate 还是 Testbench。

但 native Vitis 的 `compiler_failure` 有优先处理路径：先核验 build manifest 和源码 hash，再把 `source_roles`、compile units、work directory、execution 传入 `resolve_source_owner()`（`agrefactor/runtime/csim_stage.py:277-305,992-1008`）。所以不能据 fallback 调用直接断言整个 CSIM 编译归责都缺失。当前代码行为与“缺少 provenance 就保守返回 unknown”一致；现有测试只覆盖编译错误分类，没有明确测试这个 fallback 应当 unknown 还是应消费某个可用映射。设计意图仍待决定。

## 3. 修复授权与额度

`FeedbackRouter` 仅生成非执行性的 route decision；实际修复还要通过 `RecoveryPolicy`、对应 orchestration、预算和 fresh validation。Candidate repair policy 接受 Preflight、Public CSIM、CSYNTH、Public COSIM；Testbench repair 只接受 Preflight、Public CSIM、Public COSIM；Hidden stage 在 policy 开头即拒绝（`agrefactor/recovery/policy.py:110-133,240-330`）。

当前默认限额和账本关系：

| 组件/上限 | 当前实现 |
|---|---|
| Candidate | Public CSIM/COSIM 有各自 stage lane；CSYNTH、Preflight 使用 Candidate 总 lane；额外 `candidate:repairs_total` 聚合键跨这些 lane 计数。默认总 Candidate repair 上限为 3。 |
| Testbench 正式修复 | Preflight、Public CSIM、Public COSIM 各自有独立 key，默认各 3；`_additional_limit_keys()` 只给 Candidate 增加总量 key，没有 Testbench 聚合 key。 |
| Hidden 正式修复 | `hidden_repairs` 必须为 0；Hidden recovery stage 被拒绝。 |
| 全局动作上限 | `total_recovery_actions` 默认 5，按同一个 RecoveryLedger 的 run-level 计数。 |
| R5 AI/记忆 repair | 没有独立额外的 AI repair quota；进入 Candidate repair 时仍走 Candidate policy/ledger 和 budget。 |

正式 Testbench recovery 在 `CandidateRepairIntegration` 中要求 agent-safe feedback、blocking feedback owner 全为 Testbench、限定 Public 的 validation state，并要求 `testbench_revision_authorization == auto_public_bounded`；之后每次修改先 `ledger.reserve()`，再调用 `TestbenchRepairLoop` 并复验（`agrefactor/runtime/candidate_repair_integration.py:1186-1245,1264-1366`）。所以正式 Hidden 评测反馈后的 Testbench 修复当前不会发生。

但 v0.3 要求的额度合同尚未实现：

- 正式 Public Testbench 修复的 stage lane 不互相聚合；跨 Preflight、CSIM、COSIM 仍可能分别使用本阶段额度，另外受全局总动作上限约束。
- `flow/tools/tb_optimizer.py` 的生成资格修正按 trajectory 保存 artifact event counts，`max_repairs` 主要限制该 trajectory 的 Testbench repair requests 和 round 数。Hidden generation 使用自己的 `max_repairs`，多个 trajectory 可由线程池并行；它没有接入 `RecoveryLedger` 的 Public/Hidden Testbench 总账本（约第 2048-2064、2211-2212、2504-2510、2691-2705、3903-3921 行）。
- Stub 有独立 artifact event 记录和局部生成动作，但没有统一 Stub component ledger；Testbench 的 `max_repairs` 检查看的是 Testbench `repair_requests`，不等同于“任何被修改组件的共享预算”。
- 因此当前既没有 Public/Hidden Testbench 两本组件账，也没有“正式 Testbench 修复 + 同可见性生成资格修正共同扣同一本账”。这是 v0.3 中已确认的改造目标，不是当前行为。

## 4. Hidden 边界与生成资格修正

正式 Hidden 评测反馈后的修复有多道阻断：RecoveryPolicy 拒绝 Hidden recovery；catalog 对 Hidden 隐去 repair actions；`DiagnosticEventProjector` 拒绝把 Hidden evaluation 投影成 agent event；R5 memory payload 也禁止 Hidden、Testbench 等内容进入 Candidate memory payload。相应行为有 policy、projection 和 memory tests。

需要把这条边界与 **Hidden Testbench 生成阶段** 分开。`tb_optimizer` 在 Hidden suite 尚未冻结时以 `hidden_generation=True` 工作；它要求冻结的 Public-derived ABI，按自己的 original/interface/compile/coverage qualification 运行，并把先前生成的 Hidden Testbench 及生成期诊断传给 Hidden Testbench 生成模型。prompt 明确标记这是 Hidden generation，要求反馈不得传给 Candidate repair（`flow/tools/tb_optimizer.py:1208-1363,2048-2064,2504-2580,2691-2754,3903-3921`）。

这说明代码允许**生成器修正自己正在生成的 Hidden Testbench**，不等于允许根据正式 Hidden 评测结果修 Candidate 或 Testbench。未来 memory/case 合同需要明确：生成期 Hidden 诊断可在生成器内部使用，但不得因此写入跨运行可检索经验或 Candidate prompt；正式 Hidden 评测内容仍不得进入这些通道。现有本地 `max_repairs` 不是 v0.3 要求的 Hidden Testbench 组件额度。

## 5. 案例、经验、R3/R5 与 AI 诊断

目前有三类相邻但不同的数据结构：

- `DiagnosticEvent` 关联 run/validation、诊断、owner authority 和证据引用，但没有 v0.3 所需的统一 `case_id` + 多个 `attempt_id` + 最终 case outcome（`agrefactor/evidence/diagnostic_event.py:271-362`）。
- R3 `DiagnosticEpisode`/`EpisodeStore` 是 shadow episode/gate 数据结构；R4 有 repair episode；R5 append-only ledger 接受 `r3_shadow`、`r4_repair` 两类 episode。R5 ledger 可以保存验证 outcome，但 reduction 只接收 verified positive/negative episode。它们不是“每次阻塞故障一个 case、每次修复一条 attempt”的新 Case store（`agrefactor/recovery/memory_gate.py:144-253`，`agrefactor/recovery/r4_episode.py:64-215`，`agrefactor/recovery/episode_ledger.py:102-154,188-239`）。
- R5 pattern revision/payload 带 Lifecycle、snapshot、authorization 和 candidate-only 约束；A0–A6 仍包含 `full_lifecycle_gated`。这些是旧实验机制，不能等同于用户已确定的无自动生命周期的新设计。

R5 的普通产品默认 profile 是关闭的；`r5_profile.py` 说明它是内部 experiment profile，不是 CLI mode。选择 arm 还需要完整内部 `R5RuntimeBinding`。已绑定的 `approved_memory_snippets` 可进入 Candidate prompt，但这些片段由 experiment 在运行前提供；没有发现修复每次失败后都依据最新 evidence 重新 query 的 retriever callback。Testbench 没有对应的 memory prompt binding（`agrefactor/runtime/r5_profile.py:1-11,31-110`，`agrefactor/runtime/r5_binding.py:31-155`，`agrefactor/product/source_bootstrap.py:778-791,2203-2238`）。

当前 R4/R5 有 Candidate-only、带 evidence reference、拒绝直接 accept 的 advisory schema；R4/R5 experiment integration 消费符合条件的 R2 shadow advisory，并经校准、Gate、policy 后才可能尝试 Candidate repair。它不是默认产品的通用诊断助手。`DiagnosticAdvisory` 没有 `registered_check_id` 或本地证据采集请求字段；普通 `RecoveryPolicy.ADVISORY` 还要求 unknown owner、physical launch、`evidence_complete=true`，只允许 Public CSIM/CSYNTH/COSIM（`agrefactor/recovery/advisory.py:33-150`，`agrefactor/recovery/policy.py:314-329`）。

未发现新设计的 CLI 开关、`derive_experiences` 命令或 Case→Experience 自动整理入口。R5 实验可以从其 episode/pattern 流程构造受审核约束的 memory payload，但它仍依赖旧 lifecycle 和预绑定 snapshot，不满足当前已讨论的“case 结案后自动幂等整理经验、规则晋升另行人工审核”。

## 6. 本地证据补查

现有可复用件包括阶段 parser、编译/链接诊断解析、artifact/report reader、source-role/compile-unit owner resolver、CSYNTH artifact feedback、CSIM/COSIM 结构化结果，以及固定的 Original isolation qualification。它们由本地阶段代码按确定路径调用。

在 `agrefactor/` 和 `flow/` 中没有发现通用 evidence collector registry、带 ID 的检查清单或由模型选择 ID 后交本地 dispatcher 执行的接口。现有 advisory 输出 evidence references 和归因建议，不输出受登记的下一项检查 ID。当前不能回答“已登记本地补查范围究竟有哪些”，因为这个新检查层尚不存在；本地可复用采集器需要逐项从已有调用点盘点，而非把现有任意工具命令视作已登记检查。

## 8. 测试结果与剩余风险

目标测试运行命令为 `PYTHONPATH=tests python -m unittest ...`，运行了 catalog、catalog projection、feedback router、CSYNTH bounded trial、CSIM stage、recovery authority/policy、R3/R4/R5 memory、Hidden generated differential 和 Hidden Testbench/Stub qualification 模块。结果：137 tests，5 failures、3 errors。

失败/错误集中于：

- `test_missing_candidate_declaration_retries_testbench_with_evidence`：运行时被 `freeze_public_type_contract` 拒绝，报 Candidate type contract incomplete。
- `test_frozen_abi_can_use_testbench_source_package_types`：同样在解析阶段得到 incomplete type contract。
- `test_k1_repairs_initial_hidden_abi_drift_once`：抛出“Testbench changed the externally frozen Public-derived ABI”。
- `test_noop_definition_preserves_attributed_forward_declarations`：三个属性子测试因资格执行包装改写了 `testbench.cpp` 内容而失败。
- `test_missing_observed_frozen_declaration_is_explicit` 与 `test_unparseable_frozen_abi_is_not_silently_accepted`：代码抛出了 type-contract-incomplete 错误，但断言期待的错误文案不匹配。

这些结果不能直接判定代码或测试哪边过时，但它们说明当前 Hidden Testbench 资格修正路径并非测试全绿；在把该路径纳入新的 Hidden Testbench 额度或作为基线前，需要单独确认这些失败的预期行为并修复测试/实现合同。

## 9. 代码审计无法替代的设计决定

1. 经验检索的硬过滤字段、相似度方法、排序、阈值、Top-K，以及正负经验在 prompt 中的格式。
2. `unknown` 但证据完整、证据缺失、证据矛盾三种情形下，AI 各自何时参与；现有 advisory 的 evidence-complete 门槛是否沿用。
3. 每条目录规则真正需要的专项诊断证据和验证合同；代码里的通用字段名不足以反推这些要求。
4. Public/Hidden Testbench 额度数值、单次多组件修改如何扣总动作，以及生成资格修正的哪些本地信号可接受。
5. CSIM fallback owner 分支是刻意保守，还是应继续找得到/生成 source-role provenance。
6. 旧 R3/R5 代码和既有实验数据的保留、隔离和标注方式。
